## CI failure and repair

Only Playwright failed. The paginated-feed test loaded 32 cards, opened an event and closed it, then found the card approximately 295–304 pixels away from its saved viewport position on all three attempts. Lint/contract tests, pipeline unit tests and the production build passed remotely; 26 other browser tests passed.

The intercepted modal kept the feed mounted but discarded its return marker without restoring the card anchor. A mounted feed can still reflow. The patch in `EventModal.tsx` restores the saved card position after releasing the scroll lock, falling back to the saved scroll offset if the card is unavailable. It checks the return URL, preserves the standalone-page restoration path, and then clears the marker.

The original case passed repeatedly on macOS. A new viewport-resize variant reproduced the missing restoration before the fix and passed afterward. The exact Linux trace's source of layout displacement has not been independently reproduced locally.

Local verification after the patch:

- All 28 Playwright tests passed with `CI=true` and retries disabled, including refresh, history, filters, pagination, mobile, and the new resize regression.
- All 133 unit/contract/integration tests passed.
- Lint passed with the untracked Python virtual environment excluded: `npm run lint -- --ignore-pattern 'pipeline/.venv/**'`. Plain local lint also traverses Playwright's vendored JavaScript inside that environment; CI runs lint before creating its Python environment and did not have that failure.
- Production build passed with placeholder Supabase credentials; `git diff --check` passed.

The patch is local and uncommitted. A new GitHub CI run on the patch is still needed to confirm Linux behavior.

Publication being green with these refusals is deliberate current behavior: it distinguishes non-retryable grounding refusals from retryable operational failures. Ordinary reruns reuse the refusals. Recovery requires evidence/prompt review and a targeted `--retry-failed --source ...` dry run; no archive-wide retry or publication was performed.

### Oversized image recovery will keep failing without a size-aware upload path

`ucrmbb` post `3963240207299062111` failed flyer upload with HTTP 413. The live `event-flyers` bucket allows 5,242,880 bytes, while `_upload_flyer` uploads original bytes without size normalization. Its extraction retained OCR but has no durable `image_url`. This is a real recovery-path limitation; repeated attempts with the same oversized image cannot fix it.

This particular post says “Another week of work in the books” and was already classified `uncertain`, with no event IDs. Thus the failed upload did not suppress a published event. A future repair should normalize only the uploaded display image to the bucket limit while retaining original OCR/source evidence.
